Everyone believes reading input files is a simple task. Are you one of them? Look closer, and you realise that there are issues you haven't even thought about; issues that may come back to haunt you long after you have settled on a specific file type in your solver to use.

Most people will either use the file types they already know or the first that they found through googling. If we all picked our life partner the way we pick file types, we'd all be stuck with somebody named .tmp; technically functional, but nobody really wants them around long-term.

There is a lot of depth to a seemingly simple problem, and so, in this article, we will explore the file types that exist (and are in use) for reading and writing input/output files which are either produced or consumed by CFD solvers.

By the end of this article, you will know more about the best file types to use in CFD than, let's face it, 99.999999% of the population (approximately). This also means that once you know all the pros and cons of each file type, you know when to use which, and your solver will never run into unforeseen issues without you knowing why.

What is serialisation and why you should care about it

CFD has one big problem: complexity. If all you ever want to do is to run 2D channel flows for incompressible fluids at a Reynolds number of Re=100Re=100Re=100, you may skip this section (and maybe you should question your life choices). But, say you wish to run simulations of anything north of 10 million cells, perhaps an unsteady simulation, and you have no idea what your time step is (as it is computed adaptively from the CFL number), then how do you know for how long the simulation will run?

We simply don't know, is often the answer. Even if it is a steady state simulation, we have no idea how many iterations we need. Last time I checked, whenever I submit a simulation to our HPC cluster, there is no option to say run for as long as the simulation needs mate. I typically have to specify how long I want to use the cluster, with a hard limit set to 5 days (at least on our own cluster in Cranfield).

Or worse, I know exactly how long it takes, and for the sake of argument, let's say it takes 7 days. I cannot run this simulation in one go, I will need to split it across 2 sessions. This means: start the solver, read the mesh, start the simulation, iterate, write the solution, stop the solver, resubmit the same simulation, start the solver again, read the mesh and the previous solution, iterate, write the solution, hope the simulation finished.

While this work-around may be Cranfield-specific (although I am sure other researchers elsewhere will have similar time-limitations for how long they can use their cluster), the restart-from-previous-solution part isn't. Restarting a CFD simulation from a previous solution is a fairly common practice.

If you have ever written your own solver, there will be a point where you start to think about implementing a restart file. If you have reached that point, but have never heard about serialisation, wonderful hacks start to emerge in your solver because you are trying to reinvent the wheel, finding a solution to a problem that has already been solved, over and over and over again!

But if you haven't, you may ask, what's so difficult about it? And, yes, you are right, on the surface, this is an easy problem. Store the solution variables (pressure, velocity, etc.) and then read them back when you need them, right? It couldn't be simpler. OK, let's say you implement the time stepping with a second-order backward scheme. It is fairly popular since it is easy to implement and has second-order accuracy in time. It reads:

∂ϕ∂t≈3ϕn+1−4ϕn+ϕn−12Δt(1) \frac{\partial \phi}{\partial t} \approx \frac{3\phi^{n+1} - 4\phi^n + \phi^{n-1}}{2\Delta t} \tag{1}∂t∂ϕ​≈2Δt3ϕn+1−4ϕn+ϕn−1​(1)

This is correct as long as Δt\Delta tΔt is constant. If you, instead, implement this scheme in a solver where the time step is changing at each time level, then you would have:

∂ϕ∂t≈3ϕn+1−4ϕn+ϕn−1Δtn−1,n+Δtn,n+1(2) \frac{\partial \phi}{\partial t} \approx \frac{3\phi^{n+1} - 4\phi^n + \phi^{n-1}}{\Delta t_{n-1,n} + \Delta t_{n,n+1}} \tag{2}∂t∂ϕ​≈Δtn−1,n​+Δtn,n+1​3ϕn+1−4ϕn+ϕn−1​(2)

Here, Δta,b\Delta t_{a,b}Δta,b​ is the time step between time levels aaa and bbb. So, if you now store only the solution of your velocity and pressure, but not the time step information, i.e. Δt\Delta tΔt, how will you continue your time stepping once you restart your simulation? If you only store the flow field, but not the time step information, you will see that later in your result, e.g. looking at a time series of a variable.

So, you need to store the time step. Not just one, remember, the backward scheme needs both Δtn−1,n\Delta t_{n-1,n}Δtn−1,n​ and Δtn,n+1\Delta t_{n,n+1}Δtn,n+1​. So store both.

Ok, so we got the time step stored. What about residuals? We typically compute them as:

res(ϕ)=∑iN(ϕin+1−ϕin)2(3) res(\phi) = \sqrt{\sum_i^{N}\left(\phi_i^{n+1}-\phi_i^n\right)^2} \tag{3}res(ϕ)=i∑N​(ϕin+1​−ϕin​)2​(3)

This is the L2-norm of the generic flow variable ϕ\phiϕ (i.e. this could be pressure, velocity, temperature, etc.). The problem is that pressure, for example, may have rather large differences. Using SI units and assuming our simulation takes place around normal mean sea level operating conditions, we have pressure values of the order of 10510^5105 Pa. At the same time, the velocity may be of the order of 1 m/s or so.

If we assume that both the pressure and velocity change by exactly 1% between iterations, we have 0.01⋅105=103=10000.01 \cdot 10^5 = 10^3 = 10000.01⋅105=103=1000 for the pressure, and 0.01⋅1=0.010.01 \cdot 1 = 0.010.01⋅1=0.01 for the velocity. This is exactly what the residual is, i.e. it characterises by how much the flow variable changes between time steps (or iterations), in this case 1%.

If we now tried to plot this residual over time/iteration, we have 5 orders of magnitude separating our pressure and velocity residuals. To make the comparison of residuals easier for us, we typically normalise the residuals by the residual that was computed at the first iteration.

If we assume that the example given above was for the first iteration, then we could state that our normalisation factor for pressure would be pres,0=1000p_{res,0}=1000pres,0​=1000, and for velocity it would be ures,0=0.01u_{res,0}=0.01ures,0​=0.01. If we now divide both of the residuals by our normalisation factor, we have 1000/pres,0=1000/1000=11000 / p_{res,0} = 1000 / 1000 = 11000/pres,0​=1000/1000=1 and 0.01/ures,0=0.01/0.01=10.01 / u_{res,0} = 0.01 / 0.01 = 10.01/ures,0​=0.01/0.01=1. In other words, our residuals now all start at 1, and so, we can easily see how they compare against each other.

So, we want to restart our simulation. If we want to have a clean continuation of our residual computation, we need to store the normalisation factors pres,0p_{res,0}pres,0​ and ures,0u_{res,0}ures,0​ as well.

I could go on; the bottom line is, there is always additional data, let's call it the solver metadata, that we need to store. And you may say, ok, easy, I got this, I will just write a text file alongside my simulation, where I store all of this data, and move on. Sure, you could, but have you considered how you would do that? Let's stick with the residual normalisation factors, for a moment, and think the process through.

How would you store that data? Plain ASCII, or would you go binary? If you store it as ASCII, how many digits do you write out? A fixed amount? Do you let C++ decide? Do you use floating point or scientific/exponential notation? If you use binary, are you using big-endian or little-endian notation (and do you know how to change that if you need to)? Do you know about endianness or are you happy for the catastrophic bugs that will come your way if you don't?

If you run in parallel, are you storing one file per core or per simulation? If you restart your simulation, but now using a different domain decomposition, will that affect your restart information? What happens when you need to add additional information to your restart file, but some people are still using your old version of the solver, will they now be unable to restart their simulation because their restart files are outdated?

You may think this is a bit over the top. If you do, try it for yourself. Write out the normalisation factors as plain ASCII, however you please, and see if you get a convergence history without any bumps. Sure, you can achieve it, but only if you really thought about it beforehand. I have because I spent too much time trying to figure out why my residuals were looking strange after restarting.

So, restart files aren't necessarily the best way to store information, instead, you want to serialise your solver. Serialisation is the process of looking at what is currently stored in memory (RAM) and writing that to disk, so that next time you are running your solver, you get the exact same state in RAM (byte-for-byte identical).

class Residual {

public:

    std::ofstream out(filename, std::ios::binary | std::ios::out);

    out.write(reinterpret_cast<char*>(&normFactor), sizeof(normFactor));
    // if we wanted, we could write other stuff to disk here as well, omitted here

    out.close();
  }

  // this is known as deserialisation

    // open file from which to read the serialised information
    std::ifstream in(filename, std::ios::binary | std::ios::in);

    in.read(reinterpret_cast<char*>(&normFactor), sizeof(normFactor));
    // we could read other variables here, too
      
    in.close();
  }
};

Here we have the Residual class that contains our normFactor, which we can write to disk through the serialize() function. We can also read the file again through the deserialize() function. In each, we open a file in binary mode (opening through std::ofstream and reading through std::ifstream), as indicated by std::ios::binary.

When we write to or read from a binary file, (i.e. out.write() or in.read()), we are using reinterpret_cast<>() here. If you are not a hardcore C++ person, it may be the first time you see it, and that is a good thing. We should never use reinterpret_cast<>() UNLESS we know what we are doing (it took me very long before I felt comfortable using it, I am not sure if I actually do feel comfortable with it).

C++ is a type-safe language, that means, each variable has a type and that cannot change (if we can ignore std::any for a moment, which is an odd addition for a type-safe language (you can change types here)). Each type has a specific size in memory. For example, a double typically stores variables with 8 bytes, while an integer stores variables with only 4 bytes.

But, not only do different types require different amounts of storage space (you can think of each byte as being represented by one bucket of memory), but their type also signals to the compiler how these bytes should be arranged. For example, floating-point numbers are written using the IEEE 754 standard, which is very different from how an integer is stored, or a class, or a pixel of an image, or ...

This is where reinterpret_cast<>() is coming in. It essentially tells the compiler "shut up, I know what I'm doing" and the compiler will allow you to do whatever you want (with your types). Here, we are converting now a variable (normFactor), which is a double, to a char, i.e. raw characters. It doesn't make sense to write a double as text, but, we have to do that because the write() and read() functions only know how to write chars.

Furthermore, by writing everything as a char, we essentially tell C++ to write all of our bytes that our double holds as it is, it should not interpret this variable as a double (and potentially change bytes when writing to disk). This removes the issue I mentioned earlier (i.e. potentially losing accuracy when we read/write our variables to disk; after reading we have a byte-for-byte identical copy).

One more thing, we are not actually reading or writing chars, but, instead, char *, i.e. a pointer to a char. I know, I shouldn't bring up pointers, everyone loves them, but, in a nutshell, if we write to a char, we can store exactly one character. If we write to a char *, we can write several characters (think: a word, or a sentence, or an entire article on cfd.university). This is just a C++ quirk we have to live with.

So, since we write to a char *, we also have to use a pointer double * as our source. But, since a pointer is just pointing to a specific memory address, we can use the address of operator in C++ to get that from our double, and that is why we provide &normFactor, and not just normFactor to reinterpret_cast<>().

The second argument to read() is the number of bytes to write. For that, we use the sizeof() function, which you can pass either a variable or a type directly. So, both sizeof(normFactor) and sizeof(double) would work equally well here.

Therefore, this example shows how we can write and read, byte-for-byte identical copies of variables, to and from disk. I should add that I have structured this class here in this way just for this example, but for a real solver, you want to extract the serialisation and deserialisation logic into its own class.

If we didn't do that, we would have to write the same serialisation/deserialisation logic for each class, violating the DRY (don't repeat yourself) principle. Each class should also only have one functionality (single responsibility principle); doing both residual calculations and serialisation is a violation of that principle.

There still is one big problem, and we have not addressed that yet. Endianness. When we write a variable, say, a double, which consists of 8 bytes, we haven't actually defined which way around we want to write it. If we imagine these 8 bytes being neatly placed in memory into 8 buckets of memory storage, how should we write and read them? Have a look at this 4 byte (32 bit) integer and how it could be written to memory:

We can either write/read a variable from the front (big endian) or from the back (little endian). Different hardware will use different conventions, although little endian seems to be what you will most often find these days. Just imagine you run your solver on a cluster, get all the results back, copy them to your PC to look at the results, and they are all just numerical noise. It could be that your cluster used a different endianness to your PC. It's something I have never come across, but that is something that can happen.

So, we also need to take care of the endianness if we want to avoid any future bugs (or release our code to users who potentially run your code on all sorts of exotic hardware, did you know that AMD released CPUs with only 3 cores?! See AMD Phenom 8750B Triple-core for reference).

JSON

If you ever had to work with an exchange format to store metadata, it is likely that you will have come across .json files already. I start with them because, in my view, it is likely the one easiest to get started with (though, spoiler alert, probably not the best one to stick with).

JSON stands for JavaScript Object Notation, and so the question is justified, why would we be dealing with something JavaScript specific if we are likely working with C/C++, Python, or dare I even say, Rust? Well, history (to the best of my knowledge anyway).

When I was in high-school, we had to learn about this new technology, called the internet (it had been around for some time at that point, but we are talking still pre-YouTube era). At that point, websites were mainly HTML for formatting, CSS for styling, and PHP for database integration. The look and feel of those websites really was something special, and this website has some screenshots that are pure nostalgia (but I am glad we have moved on).

While we had to learn how to code our own websites using these three frameworks (using notepad as our code editor), a new kid on the block was gaining in popularity: JavaScript. The history around JavaScript itself is fascinating, being created by a single person in 10 days, and that quick-and-dirty prototype developed in the 1990s has become one of the most used programming languages nowadays, which includes many of its original flaws (as you would expect from a quickly put together prototype).

JavaScript wasn't standardised, and we were living in a pre-google era, so Internet Explorer had a market share of 95% and, of course, Microsoft being Microsoft, saw JavaScript, adopted it, but changed it fundamentally. Because it had the highest market share, whatever Microsoft did was essentially the JavaScript standard (even though it originated from the Netscape browser (now Mozilla Firefox)).

It also meant that due to its incompatibility with pure JavaScript (and the rise of Chrome, which adopted pure JavaScript), the days of Internet Explorer were numbered. It's a bit ironic that Microsoft Edge is now essentially a Chrome clone and having no popularity whatsoever.

In any case, with the rise of JavaScript and application programming interfaces (APIs), we needed a mechanism to exchange data between servers. For example, your website wants to show the local weather for each user based on their region, well, then you first need to get the region from the user, send a request to a weather server, receive a response back, and then show it on your website.

This required some form of standardised format to send data, and, this is precisely what JavaScript offered. And so, the new standard in which information could be exchanged was the JavaScript Object Notation (JSON), which would later also become the basic building block for classes in JavaScript (not an original feature).

JSON has become a pretty standard exchange format, not just on the web, but in general for configuration files or information that needs to be stored in a structured way. JSON supports text (strings), numbers, boolean values, arrays, and key-value pairs (also known as hash tables (computer science), maps (C++), or dictionaries (Python), depending on your background (if you are a computer science person, I am probably insulting your intelligence by talking about JSON)).

I have given you an example of how to use an array with the CFL number. It has three entries. What do these numbers mean? If I used this for my solver, and you had to use it to run simulations, and this is all you got, then you would either have to dig through the source code (if that is available) to figure out what these three values mean, look at the documentation (if it bothers to document what goes in here), use an LLM and hope it will not hallucinate, or, the approach 99% of people will take: guess and pray it is correct.

In this example, 1e-6 and 1 denote the lower and upper range for the min and max time step I want to allow, while the third argument is the CFL number itself. Thus, I don't want to allow time steps to be smaller than 1e-6 or larger than 1, regardless of what the CFL number-based computed time step is.

It would be really handy to have comments to communicate that with the user, but, since JSON was only ever designed to exchange information between servers (without humans ever reading them), comments were never part of the JSON standard. There are extensions (like JSONC (JSON with Comments)), but comments, by default, are not supported.

First, we define a common case setup. We give this case set up an anchor using the &caseBase identifier. This means we can now refer to case (and all of its sub-entries) through the variable (anchor) &caseBase. We define the case setup as before, but then, we also introduce a new key-value pair called cases.

In cases, we have three separate cases; coarse, medium, and fine. Each of these cases is inheriting the base case through <<: *caseBase. Here, *caseBase is an alias and references whatever was defined inside the anchor &caseBase. The <<: syntax simply states that we should take everything from the alias (caseBase) and dump it here.

Once we have done that, we overwrite the meshing node by specifying new values for numPointsX and numPointsY. We don't have to respecify everything that is stored in meshing, we can overwrite only those parameters we want, in this case it just so happens that we overwrite everything within meshing.

Besides the already very useful toml::find function, there is one more that is extremely useful if you are dealing with option parameters. Imagine your solver can do both fixed time stepping, and adaptive time stepping based on a fixed CFL number. A single precision float has space to store 32-bits. It uses 1-bit for the sign, 8-bits for the exponent, and 23-bits for the fraction (compared to my 3-bit in the example above). That will make the gap between floating-point numbers smaller, but it does also show that we always have a finite representation of floats; we will never be able to represent all possible floating-point values!

However, just like you can seemingly get out of any trouble if you are rich enough, you can also solve the problem here by more advanced hardware. Instead, we use 64-bit doubles, where we still use 1-bit for the sign, 11-bits for the exponent, and 52-bits for the fraction. This will be enough for all practical cases!

HDF5 / CGNS / NetCDF

Cast your mind back to (this sentence autocompletes in my mind very differently) the time we talked about CGNS and HDF5. We have already looked at these two file types, but not yet NetCDF, which stands for Network Common Data Form. If you have not read either of these articles, or you have no idea about what either format does, let me give you a brief overview of each:

CGNS: The CFD General Notation System, or CGNS, is a data format that aims to be a portable and all-inclusive data format for CFD. By portable, I mean you should be able to write the file in one CFD software, and then read it back in another CFD software. The best analogy I always use is to think of CGNS as the PDF file of CFD simulations, i.e. it is a specific CFD file format that can be understood by any piece of software (like PDFs are universally accepted to display a document).

By all-inclusive I mean a CGNS file wants to store everything a CFD simulation may need. It mostly comes down to the mesh and the corresponding solution, so the dream is you create a CGNS file in your mesher, then read it into your solver to run the simulations on, then write the solution to the same CGNS file, and then look at it in your favourite post-processor.

That's the dream, I don't think it exists outside NASA. Every CFD solver I have ever used sees CGNS as an add-on, a nice-to-have, but not as a first-class citizen. At best, it is there to show support for the cause, but every software then falls back onto using its own file format. In my view, the CGNS file format is (too?!) ambitious, meaning that there are different ways how to interpret it, and that has caused incompatibility issues.

Maybe we'll fix them one day, but when I wrote my first CFD solver and I believed in the same dream, I wanted to adopt CGNS as the main file format and most of the time I spent debugging issues with getting CGNS to work with at least one mesher (ICEM-CFD, oh the joy). I had Pointwise available as well (now bought by Cadence, who rebranded it to the-super-high-fidelity-cadences-in-house-mesh-generator-formerly-known-as-pointwise, or something to that effect (which I refuse to call it)), but Pointwise and ICEM-CFD would write CGNS files differently.

In any case, CGNS works by storing data in a hierarchical, node-based form. Each node has a standard name/type, so it can be read by other software, so the structure of a CGNS file is locked in, you just have to find the right node to write your data into. For example, there is a node for the mesh and one for your solution. Each variable is already defined, so you have to write your data using the predefined variable identifier (VelocityX, VelocityY, and VelocityZ instead of u, v, and w).

In theory, you could also write additional, solver meta-data into the CGNS file if you wanted to store additional solver configurations. The argument is that if you already use CGNS for your mesh and solution data, you may as well store the solver inputs alongside so you can make sense of this later.

However, CGNS files are binary files, and we cannot simply open them, unless we use specialist CGNS inspection tools. So, it is impractical to write solver configurations into them. If you wanted to set up a new case, or change the settings of an existing one, you would have to first launch a different application to access your input file. This is too complicated, only the French would do it this way.

HDF5: This file format is best described as "a compression format for scientific data, on steroids". Virtually all CFD software that want to reduce file sizes use HDF5 these days. Even CGNS is based off HDF5. NetCDF (we are getting to it) also uses HDF5 in the backend.

Just like CGNS, HDF5 files can be thought of as a node-based representation, where we write data (like the mesh, or the solution arrays) under a specific node. Unlike a CGNS file format, an HDF5 file wants to support all types of scientific applications, and so there is no pre-determined structure, and we can nest nodes however we want, or name them however we want.

HDF5 files are also somewhat easier to write than CGNS files, as you can essentially come up with a structure for your data yourself and then just write it, while you have to identify the correct node in CGNS to write your data into.

NetCDF: We have not talked about NetCDF around here on this website. And for good reason. I made the comparison between TOML and INI files before, where I said that INI files are like the toddler brother of TOML files in terms of capabilities. That is, TOML has support for headers, nested key-value pairs, and even types, while INI files have single-header only, no data type support, and everything is a string.

The same analogy holds here where NetCDF is the incapable toddler brother of HDF5, the strong, alpha-male older brother. NetCDF (which always translates to NetCFD in my head, I cannot be the only one ...) is, in essence, a file format that allows us to store arrays. No nested nodes, just plain arrays named arrays. So, in theory, it is very simple to pick up, but just like HDF5, we have to go through a library to write these files and the library follows 1980s rules of using as many cryptic names as possible. It's no joy.

Under the hood, NetCDF has switched to storing its data using HDF5. Let's unpack that. HDF5 offers a wide range and flexibility in storing data. NetCDF offers a fraction of this, and only achieves comparable speeds because it uses HDF5 as well. Brilliant. It's like me releasing my own open-source CFD solver, which is just a bash script calling OpenFOAM routines and solvers, but I have removed all support for unstructured grids, parallelisation with MPI, and even turbulence modelling capabilities.

You may ask yourself, what is the point of NetCDF then? I don't have an answer.

What it does mean, though, is that I have made this section incredibly simple for myself. I don't think there is any point in showing you how to write a NetCDF file, as you will be able to do much better with HDF5 and CGNS. Though, I wouldn't recommend either for storing solver configurations. These file types exist for storing your solution (i.e. array-like structures), and so using these files to store solver configurations is a bit like eating popcorn with chopsticks. Sure, you can do it, but why would you?

In case you must, here is my verdict on its features:

Since everything is binary, comments don't make sense here. But, we can typically provide annotations that do the same job, but we need a specialist program to read them, so these comments may also get lost. All file types have a steering committee behind it as best as I can tell, so we can be confident that the file types themselves will be maintained and do not change overnight breaking our solvers.

Since we store mostly array-like structure, there is no concept of inheritance and expressions/units, though both HDF5 and CGNS have compositions, i.e. we can link several files together (e.g. one mesh file linked with many solution files to avoid storing the mesh for each time step). But, since we store all of that in binary, we get byte-for-byte identical results, so we can be confident in storing data and reading it back exactly as is, good for serialisation tasks (and that is what we would use it for).

In terms of integration into our solver, we had:

The files don't have any in-built mechanism to support error messages, that would happen at the time of going through the library. As a developer, you may see errors, but not necessarily as a user. Binary files without any error messages are difficult to debug in case things go wrong. Regardless of which file type you go for, there will be a library you have to go through, and these can bring in heavy dependencies (well, mostly HDF5, but CGNS also builds with TK/TCL if you want GUIs for some useful CGNS inspection tools).

HDF5 got its own article, CGNS its own series with 6 articles in total. If I can fill an entire series on one file type, that probably means there is a lot to learn. So it is not something you can pick up like any of the other file types we have looked at thus far, but usually, you also learn these file types because they are foundational to your solver infrastructure.

What it does give you is that extra bit of performance, especially when we are looking at parallel performance. HDF5 has dedicated support for writing distributed data, and since CGNS and NetCDF are built on it, they inherit this at no extra cost to them. It is the reverse of Pareto's law. We say that 80% of the results come from 20% of the work. Here it is the reverse; to get the last 20% of performance out of your CFD solver, you have to spend 80% of your time to implement and fine-tune HDF5, CGNS, and if you must, NetCDF.

My recommendation, though, if you have any say in this: avoid NetCDF, adopt HDF5 for any data storage, not solver configurations, and use CGNS if you have to, or you have a specific use case (i.e. reading a mesh from a mesh generator and CGNS is the easiest file format you can get out of it).

However, one thing we can probably all agree on is that simply separating input values by commas is likely the simplest way of representing data. There is one big advantage, though, that CSV files provide us. And this is where the left to right parameter reading actually will help us. And that is parametric simulations. Let's say we want to do the same grid dependency study we have looked at in other examples, where the solver configurations stayed the same, but we changed the mesh size only. We could express that in our CSV file as:

caseID,meshing.numPointsX,meshing.numPointsY,boundaryConditions.north,boundaryConditions.south,boundaryConditions.east,boundaryConditions.west,solver.turbulence,solver.model,solver.CFL 1,64,64,Dirichlet,Neumann,Neumann,Dirichlet,true,komega-SST,"[1e-6,1,10]" 2,128,128,Dirichlet,Neumann,Neumann,Dirichlet,true,komega-SST,"[1e-6,1,10]" 3,256,256,Dirichlet,Neumann,Neumann,Dirichlet,true,komega-SST,"[1e-6,1,10]"

In terms of integration, we had:

CSV files don't have any way to emit error messages, but when something goes wrong, it is usually because we placed our commas incorrectly. The most difficult to debug issue is likely when you start using whitespaces and expect them to be stripped. For example, if we stored the first two entries in our config file as:

Sin #1: Parsing configuration files mid-solver run

Imagine you are on an airplane and all of a sudden, there is an unexpected change to the flight plan. If you wanted to casually walk up to the pilot and politely ask them to divert, your request would probably be politely declined. But, of course, if you bring explosives to the party and threaten to use them, you'd be surprised how much attention and cooperation you will receive.

In general, I would always advise you to travel with an explosive in your hand luggage. It is one of the best insurance policies you can have because the likelihood of having two individuals on board with a bomb is vanishingly small. It might be difficult to argue your case at security, but if you give them my explanation, I am sure they see the point.

Be that as it may, I think we can all agree, we'd all be much rather on a plane without any diversions and threats of explosives. If I board an easyJet flight to Luton airport, the pilot better takes me there. But then again, if I had a choice between landing in Luton or being diverted anywhere else, I am not sure what sounds better. I might go with the latter.

In our CFD solver, it is the same. When I tell it to run for a certain number of iterations, or time steps, and use a specific scheme or model, I would, ideally, like it to do that and not switch from an incompressible to a compressible solver, or from a k−ωk-\omegak−ω SST to a Spalart-Allmaras model mid-solver run. If I change to compressible flows, my solver will crash because it doesn't have any idea how to treat density, if I switch to Spalart-Allmaras, then my solver doesn't have any boundary conditions for ν~\tilde{\nu}ν~.

The end result? Best case, this request is ignored, worst case, the solver which was running for a few days or weeks now crashes without having stored any intermediate solution files.

Now, you may say that this is a bit of a farfetched example, why would that change mid-solver run? Because in OpenFOAM, for example, this isn't a bug, it is an explicit feature. They probably even have it as one of their USPs (unique selling points). You can go into any config files, change it, and OpenFOAM will read it mid-run, parse it, and make the necessary modifications.

It is absolutely possible to make changes mid run, but I ask, what is the point? Is it so we can start a simulation and, once it is converging, change it to a higher-order numerical scheme to reduce the numerical dissipation? If so, why not just run the simulation for a set number of iterations, make the change after we finished this initial run and then restart with the new scheme selection?

I think it is important we are able to have a deterministic way of running our simulations so they can be reproduced. You may then argue this is more for dynamic testing, but that practice just teaches the wrong behavioural patterns. We shouldn't be making any adjustments mid-simulation because we introduce randomness at best, and crash our simulation at worst.

Thankfully, we can switch this behaviour off, and there should never be a reason to switch it on in my view.

Sin #2: Silent configuration defaults that aren't documented

Many solvers have a function that is called something like lookupOrDefault(). I have used that type of function in my own solvers, I am not a saint. This function looks for a value in an input file and, if it cannot find one, assumes a default value. Now, let me give you an example that happened to one of my students, I cannot remember the solver we used, but the issue was not solver-specific, it can happen to anyone with any solver.

The student was investigating a case for which we had different results available for comparison at different Reynolds numbers. Then, instead of changing the density or the inlet velocity, the student opted to change the viscosity instead to change the Reynolds number. When the student did that, they mistyped the variable name for the viscosity. It wasn't a typo (syntax error), but a flawed logic (semantic error).

The student changed the parameter mu (μ\muμ), but the solver defined the Reynolds number using the kinematic viscosity nu (ν\nuν). It may have been the other way around, I don't recall. The behaviour of the solver was, if nu was not provided, rather than crashing and reporting that as an error, it would silently adopt a default value.

The problem was that we did not just change the Reynolds number between runs, but also the Mach number. And so, there were differences between runs, but the differences were entirely due to the Mach number, and not capturing the Reynolds number effects. We had to do that because the reference data was provided in this way, and we wanted to match that data first before moving on.

Suffice it to say, it took the student some days to track down the issue. If the solver was just honest about a missing viscosity value, it could have informed the user about it. This is bad software design, never assume default physical quantities that fundamentally change a simulation if nothing is specified. Or, if you want to, make that clear in the config file by setting a flag like useDefault = true. Now the user can look up what these defaults are and have a chance to catch physics bugs.

Sounds like a good solution at first (I am sure the engineers at ANSYS are still tapping themselves on the shoulders for a job well-done), but they violated the open-closed principle with their interface design and thus deserve to burn in hell. The open-closed principle, in object-orientated programming, states that a class should be open for extension but closed for modification.

Open for extension means that we should be able to add functionality to a class, like adding a new method (function) to it. Closed for modifications means that whatever changes I do should not affect the existing class design. This is very abstract, let me demonstrate with a simple example, we don't even need classes for that, just a simple function.

First, we rename the function so it stays a hidden implementation secret. Then, we create a new function that users were already calling before, and we no longer care what arguments the users provide. We don't even sanity check them. It is the software engineering equivalent of calling the customer service department and then waiting for an hour while repeatedly hearing the words "Your call is very important to us, please hold".

We then try to call the original function and just pass all the arguments the user provided us, you know, the arguments that are very important to us, so important that we can't even bother checking if the arguments are correct, or make sense. But, we know there is a decent chance that the function call will fail now, and so, to make sure a simulation never stops but always proceeds, we return a magic number.

It can be anything, the simulation doesn't have to be right, or the user doesn't need to know their time step computation failed. As long as the simulation progresses, users are happy. While you could argue this is still adhering to the open-closed principle (we can still call the function we wanted, and it does something), we have now turned a working function into a broken promise. The function no longer works as expected. There are no points for being technically correct when the end result is unusable.

Sin #4: Consuming proprietary file formats like petrol station sushi

Sure, I enjoy sushi as much as the next guy (that is, not at all). Honestly, raw fish? I mean, just imagine German sushi: a raw potato. Or Italian sushi: uncooked pasta. Or British sushi: a raw (Cadbury cream-) egg. Would you eat that? Probably not, so why are you still eating food that someone forgot to prepare? But going back to the analogy, let's say you actually do enjoy sushi, would you, when going to the gas station at midnight on a Sunday evening buy the last pack of sushi that is on sale?

CFD solvers, as well as pre-processors (meshing) and post-processors all use their own proprietary formats. ANSYS has their .cas.h5, Star-CCM+ their .sim, Tecplot their .plt, and the list goes on. As long as there is a common standard that everyone is implementing to the dot, there is no issue. But that isn't a realistic reality to believe in.

Every software will implement what it believes it needs. Not what it believes you need. Locking yourself into using only proprietary formats means you don't really own your own data. For example, imagine you buy a Fluent licence for a single project, but only for a year. You store all the output in Fluent's .dat.h5 format. Then, you open that in Tecplot, which you also got a licence for, for the year. You do your post-processing and everything is good. Then you return that licence as well.

A year later you need to check something in your data, but realise that you can only really read .dat.h5 files with Fluent or Tecplot. Paraview is open source, and that is what you turn to first, but it only supports the old .cas reader, and even that is flaky. You can convert Fluent data into a format that Paraview understands, but you need to modify the exported file itself. In any case, you need Fluent for that again.

This may be a very niche scenario, but one that could have been entirely avoided by simply adopting a more open and supported file format. CGNS is the obvious choice here, but again, Paraview doesn't like it that much. But with CGNS you do at least have the option of reading and converting it yourself, if you absolutely had to, so it is still a better long-term storage solution than storing your results in a proprietary format you lose access to the day you walk away from that licence.

The other issue is that you have no idea what is in the file. If there is a bug, and it is setting a solver setting you did not expect to be set, that could, in the worst case, lead to an incorrect simulation. Tracing that behaviour will become a nightmare, as it is pretty much impossible to figure that out on your own without the help of someone on the inside who is also willing to figure out whether there is a bug or not in the file format parsing.

The software community has embraced the open-source model, and it is a fantastic model; anyone can contribute, anyone can inspect source code, anyone can find issues on code and flag these. If we have a choice, we should always go for something that is easy to work with in the long term, even if software licences or workflow changes.
